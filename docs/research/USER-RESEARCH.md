# Learner and tutor research protocol

Type: how-to. Revision 3. Planned research; no recruited participants, observed impact or teacher approval is claimed. Do not contact anyone without authorization.

## Questions worth answering

1. Does applying watts and watt-hours to a schedule address an actual learning difficulty in the target course?
2. Can a novice understand the lab and make a meaningful decision with little setup?
3. Does evidence-specific support help them revise a plan without simply handing over the solution?
4. Does voice add useful control or create avoidable friction?
5. Does a tutor's evidence packet reveal something useful beyond the final result?
6. Can participants apply the concept in B and again in C after a delay?
7. What benefit remains when the alternative is a capable current assistant using the same lab and source material?

## Discovery — September 24–26 target

Seek two target learners and one STEM tutor initially. Ask about a recent real lesson, the last confusing task, their existing tools, how they knew an answer was correct and how a tutor helped. Ask for an example they are entitled to share. Avoid pitching features before understanding the problem.

Show the proposed study-hub brief only after discovery. Check relevance, numerical readability, service requirements and whether the task measures the intended concepts. If the subject feels arbitrary, align the brief with the actual course. Do not respond by adding unrelated subjects before a lesson works.

Participation is voluntary. Use adults in the first pilot, pseudonyms and minimal data. No school grades or high-stakes educational decisions. Record consent separately; audio/video recording is optional and separately chosen. No real credentials, electrical equipment or paid accounts are required for the exercise.

## Formative pilot — October 10–15 target

Aim for 6–8 learners and 2 tutors; four learners returning 24–48 hours later. The plan is exploratory and too small for a causal learning-effect claim. If recruitment falls short, disclose the actual count and use internal walkthroughs only as internal evidence.

Session, roughly 30–40 minutes:

1. Brief prior-experience and unit-understanding check; no instruction on the exact solution.
2. Open A with minimal introduction; note time to first meaningful action and requests for facilitator help.
3. Observe actions and assistance. Ask short neutral questions only after an action, avoiding tutoring during an independent outcome.
4. Enter B without conceptual hints. Preserve first outcome, retries and any switch to assisted mode.
5. Inspect the evidence packet; ask what it says and what it cannot establish.
6. Ask what the learner would have done using their existing tools and whether they would use the lesson again.
7. Schedule C only if they agree to a follow-up. Record actual elapsed time; do not fabricate a reminder or attendance.

Tutor session: inspect a pseudonymous packet, identify the relevant difficulty, choose a teaching intervention and explain what evidence is missing. Measure rough review time and disagreements. A single good quote is a qualitative observation, not proof of demand.

## Fair alternative comparison

Use two approaches: LearnSprint's integrated coach and a current capable ChatGPT Study Mode or Gemini learning experience with access to the **same lab, brief and source cards**. A plain chatbot without a simulator is an additional convenience comparison only; it cannot isolate the value of the coaching workflow.

Record actual product/date/account capabilities and prompt. Ask the participant to obtain useful guidance without supplying the hidden schedule answer. Do not disable advertised competing features to manufacture a win.

Where feasible, counterbalance order and use comparable parameter variants approved before the session. Reusing the same exact solution introduces learning carryover; disclose it if unavoidable. Prefer reporting individual traces and usability findings over a headline percentage from a tiny mixed sample. Do not label this pilot a randomized efficacy trial.

Comparison dimensions: setup/time to useful action, facilitator rescues, correct interpretation of W vs Wh, first transfer result, conceptual assistance, voice correction rate and tutor usefulness. Satisfaction alone is insufficient.

## Data sheet

| Field | Value to record |
| --- | --- |
| Participant | Pseudonym, broad study context, prior familiarity, language comfort |
| Session | Date, release/pack version, provider mode, comparator capability |
| Time | First action, A completion, B attempt, actual C interval |
| Actions | Run IDs, relevant edits, hints viewed, command corrections |
| Outcome | First and final feasibility; assisted/independent; incomplete/withdrawn |
| Understanding | Brief explanation if offered; separate human notes from numeric results |
| Experience | Confusion, friction, stated benefit, reason not to return |
| Tutor | Review duration, interpretation, useful next intervention, uncertainty |

Keep identifiable raw notes private. Public report uses consented/redacted excerpts and aggregate or pseudonymous evidence. Record missing data and withdrawals rather than dropping inconvenient outcomes.

## Iteration and reporting

Initial targets are in [requirements](../product/REQUIREMENTS.md). If people fail A because the controls are unclear, fix the interface before interpreting it as a learning problem. If B is solved by random clicking, inspect process and add a carefully framed prediction or comparison; do not force a long essay. If voice adds no value, reduce its prominence and keep specific useful commands.

Publish only actual results: “6 participants tried the prototype; 4 completed the changed task without conceptual hints” if observed, with context and limitations. Do not claim retention without the delayed session, time savings without a comparison, or effectiveness beyond this pilot. Reserve time to fix the top two observed problems before recording the demo.
